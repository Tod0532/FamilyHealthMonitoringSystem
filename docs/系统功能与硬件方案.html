1系统全景与数据流

系统只有两条数据链路：①心率自动采集链路（硬件为主）和 ②血压拍照识别链路（手机相机 + 端侧 AI）。两条链路最终都落到同一张健康数据表，再由同一套预警与展示逻辑复用。

1.1 心率自动采集链路

手环 / 心率胸带BLE 从机 · 标准心率服务 0x180D / 特征 0x2A37
↓ BLE Notify（心率值，1~2 字节）
ESP32-S3 网关（板子）BLE 主机 + WiFi STA · 5 秒一报 · 设备令牌鉴权
↓ HTTP POST /api/device/health-data
后端（Spring Boot）落库节流 + 内存实时值 + 预警评估（含冷却去重）
↓ MySQL / 内存实时缓存
手机 App3 秒轮询实时值 · 曲线 · 状态判定 · 预警列表

1.2 血压拍照识别链路

电子血压计屏幕七段数码管显示 收缩压 / 舒张压 / 脉搏
↓ 手机拍照（或相册选图）
端侧 OCR 流水线（纯本地）YOLOv8 定位屏幕 → 多头模型读 7 位数字 → 81 组增强投票
↓ 数值 + 可信度信号
录入表单（含"请核对"门禁）低可信度必须人工确认，否则不允许保存
↓ 用户确认后提交
后端 / 数据库与手动录入走同一接口与同一张表

3.2 关键器件与选型理由

部件规格为什么选它
主控模组ESP32-S3-WROOM-1（双核 Xtensa LX7 @240MHz，BLE 5 + WiFi 2.4G，8MB Flash，无 PSRAM）同一颗芯片同时具备 BLE 主机与 WiFi，省掉"蓝牙转串口 + 串口转 WiFi"两颗芯片；算力足够跑 NimBLE + HTTP。实测固件只占 RAM 15.8% / Flash 32.5%，N8 版本足够
USB-UART 桥CP2102N（板载）给 PC 提供烧写/调试串口。需要在 Windows 装 Silicon Labs 驱动（本项目已装好 v10.1.8.2466）
心率源手环 / 心率胸带，需对外暴露标准 0x180D走标准协议就不用破解厂商私有格式；胸带可靠性更高（戴上就持续广播，摘下即停）
供电5V USB 或板级 DC 输入（视具体 PCBA 而定）BLE + WiFi 共存时瞬时电流会拉高，建议独立 5V/2A 电源，不要靠电脑 USB 口
血压采集任意带七段数码显示的电子血压计 + 手机相机不需要给血压计装任何东西，零改造接入

3.3 硬件侧数据格式

BLE 标准心率特征 0x2A37 的负载按规范解析：

字节含义本固件处理
data[0]Flagsbit0=1 表示心率是 16 位（uint16 LE），否则 8 位；bit4=1 表示后面跟 RR 间期
data[1]（或 data[1..2]）心率值取值合理性过滤：25 ≤ bpm ≤ 250 才接受
后续字节RR 间期、能量消耗等不使用（本系统只关心瞬时心率）

3.5 硬件侧已知风险与对策

风险现象对策
企业级 WiFi 连不上家庭网络是 WPA2-Enterprise(802.1X)，而固件只实现 WPA2-PSK用一个能自开 WPA2-PSK + NAT 的小路由器，板子/手机/电脑都挂它；顺带绕过企业网的客户端隔离
BLE 与 WiFi 抢 2.4G 射频距离远时心率上报间歇性丢失网关靠近手环；选带 IPEX 外置天线口的板子；天线别贴着金属
供电跌落导致随机重启串口日志看起来正常，但板子莫名重启、BLE 连上就掉独立 5V/2A 电源 + USB 电流表观察瞬时压降
BLE 单连接限制板子连上手环后，手机就连不上手环了这是协议特点，不是故障：调试时看板子串口日志，或用 BLE 嗅探器抓包
一个网关只连一个心率源多人家庭需要多块板固件侧扩展多连接即可（NimBLE 已配置 MAX_CONNECTIONS=2），不必买更多板

4.2 固件启动流程

上电 → 串口 115200 初始化打印启动横幅
↓
NimBLE 初始化设备名 HealthBridge，发射功率 +9dBm
↓
从 NVS 读设备令牌Preferences 命名空间 hrbridge
↓ 无令牌则用绑定码换
连 WiFi → NTP 对时北京时间，用于 measureTime
↓
扫描 → 连接手环 → 发现 0x180D → 订阅 0x2A37成功后开始收心率通知

4.3 主循环与上报策略

判定条件动作
BLE 掉线!isConnected()等 5 秒 → 重连 WiFi → 重新扫描连接
WiFi 掉线WiFi.status() != WL_CONNECTED立即重连（最多等 20 秒）
数据陈旧距上次心率通知 > 10 秒不当作有效值；每 30 秒提示一次"确认手环戴在手腕上"
需要上报心率变化 ≥ 3 bpm 或 距上次上报 ≥ 5 秒HTTP POST 上报（含 measureTime）
上报失败网络异常 / 非 200读数压入环形缓存（容量 30 条），每 15 秒尝试补传
令牌失效HTTP 401清空令牌，下次上报前重新用绑定码换（被 App 解绑后就走到这里）
为什么是 5 秒：实时监控要求 3~5 秒级刷新。5 秒一报等于一天约 1.7 万条， 所以服务端必须做落库节流（见 5.3），否则数据库会被刷爆。 两端阈值刻意保持一致：固件按 3bpm/5s 决定"要不要发"，服务端按 3bpm/60s 决定"要不要存"。

4.4 上报报文体

POST /api/device/health-data
Content-Type: application/json
X-Device-Token: <设备令牌，首次绑定后写入 NVS，长期有效>

{
  "dataType": "heart_rate",
  "value1": 76,
  "unit": "bpm",
  "measureTime": "2026-10-19 11:32:05"
}

服务端按令牌反查设备→归属成员，自动补 family_id、数据来源 device、设备名，无需固件关心这些。

4.5 设备鉴权设计（为什么不把账号密码写进固件）

步骤谁发起接口说明
① 生成绑定码AppPOST /api/device/bind-code6 位数字，10 分钟有效、只能用一次，并指定归属成员
② 用绑定码换令牌板子POST /api/device/bind提交 bindCode + deviceSn + 固件版本 → 返回 deviceToken（只返回一次）
③ 令牌落盘板子—写入 NVS，之后不再需要绑定码；服务端只存令牌的 SHA-256，不存明文
④ 日常上报板子POST /api/device/health-data请求头带 X-Device-Token
⑤ 解绑AppDELETE /api/device/{id}令牌立即失效；板子下次上报收到 401 并清空本地令牌

这样固件里没有任何用户凭据，板子丢了也拿不到账号；用户随时能在 App 里一键解绑。

4.6 上板验证的最小路径（不需要 WiFi）

固件流程是 WiFi → 绑定 → 连手环，但WiFi 失败也会继续去连手环。所以第一次上板只要看串口，就能验证风险最高的 BLE 那半段：

把 include/secrets.h 里的 HR_BAND_NAME 留空
（固件会连"第一个广播了 0x180D 的设备"，并打印扫到的所有设备名）

预期串口输出：

[BLE] 连接 ... 已连接并订阅心率通知（请确保手环戴在手腕上）

网络层DioProvider：自动注入 JWT、统一错误处理、连接超时重试。注意它的 get/post 已经解包响应，业务侧拿到的就是 body，不要再取 .data
存储SharedPreferences（轻量配置）+ GetStorage + FlutterSecureStorage（令牌等敏感项）
双模式AppModeController 支持"真实/演示"两种模式，演示模式用本地示例数据，避免真实用户看到伪造记录

5.2 实时监控页的生命周期实现（踩过坑的地方）

这部分是"编译期不报错、真机才出事"的典型，实现要点：

  • 3 秒轮询、单请求超时 2 秒；用 _busy 标记防止慢请求与下一次轮询叠加。
  • 退到后台必须停表：页面是 push 出来的路由，退后台不会触发 dispose()，所以同时监听 didChangeAppLifecycleState；回前台立刻刷一次，不让用户先看到几分钟前的旧数字。
  • 定时器用可空字段而不是 late final。原来写成 late final Timer 却会被第二次赋值，运行时抛 LateInitializationError——而 flutter analyze 与编译都不报；更糟的是赋值右半段 Timer.periodic(...) 已执行完，异常一抛就漏出一个永不被取消的 3 秒定时器，此后一直请求到 App 退出。真机 A/B 实测：修复前离开页面后 15 秒仍有 7 次请求，修复后 0 次。
  • 数据陈旧不冒充实时：后端返回 stale=true（>20 秒无新值）时，大号心率显示 -- 并提示"以上为最近一次读数，不代表当前心率"。
  • 曲线是滚动窗口：只保留最近 30 分钟、最多 200 点，长时间停留不会无限吃内存；换设备时清空曲线，避免把两个人的读数连成一条线。

5.3 后端实现要点

5.3.1 落库节流 + 实时值缓存（两个必须同时存在）

板子 5 秒一报，但历史表不需要 5 秒一条。规则：变化 ≥3bpm 或距上次入库 >60 秒才写库，其余只刷新内存实时值。

只做节流会弄坏实时监控：如果 /api/device/latest 仍然"查库里最新一条"， 节流后最多滞后 60 秒，监控页就会一直显示旧值。所以上报时同步刷新内存实时值 （DeviceServiceImpl.REALTIME），listLatest 优先取缓存，节流只作用于历史入库。
参数取值含义
HR_STORE_DELTA_BPM3心率变化达到 3bpm 就入库
HR_STORE_INTERVAL_SECONDS60否则最多每 60 秒入库一次
stale 阈值20 秒超过则 App 显示"数据已停止"
online 窗口5 分钟设备最近 5 分钟有心跳/上报即视为在线
设备时钟超前按"间隔已到"处理否则时间差永远为负、永远不入库，等于静默掐死链路

5.3.2 预警评估与冷却去重

规则支持 > / < / = / 区间外，按级别冷却：danger 3 分钟、warning/info 30 分钟。同一次异常延续只保留 1 条记录，并前移其 update_time。

不冷却的后果（实测）：5 秒一报会把预警列表刷爆——spike 场景跑 62 秒（14 次上报） 产生 14 条预警，与上报次数 1:1；按此推算约 1.7 万条/天/成员。 冷却后同样 7 次超标上报只产生 1 条。

另一个必须处理的副作用：只按"距上一条多久"判断会把"降下来又升上去"当成同一次而吞掉，而这恰恰最该提醒。所以冷却键里带上异常是否仍在持续（内存状态 LAST_VIOLATED）——上一条也异常才算延续，上一条正常就算新事件。重启后该状态为空，会多记一条，这是刻意选的失败方向（宁可多记，不可漏报）。

5.3.3 鉴权与数据归属

  • 用户侧：JWT + Spring Security 白名单 + 自定义拦截器（两条链都要放行，只改一边会 403）。
  • 设备侧：只看 X-Device-Token，与用户体系解耦。
  • 写 health_data 必须带 family_id，否则记录入库但 App 列表看不到（列表按 family_id 过滤）。设备上报时从成员反查补上。

5.4 OCR 端侧识别实现（本项目技术含量最高的部分）

5.4.1 链路

照片
 → JPEG 兜底清理（部分手机照片自带 66KB APP1 段，会让解码抛 RangeError）
 → YOLOv8 检测模型（lcd_detector.tflite，输入 1×640×640×3）
    ├─ 输出 1×5×8400：4 个归一化框 + 1 个类别置信度
    └─ 取最高分框 → 撤销 letterbox 偏移 → 原图坐标
 → 裁剪屏幕区域 → 缩放到 224×224
 → 多头数字模型（bpressure_multihead.tflite）
    ├─ 7 个输出头，每头 10 类（数字 0~9）
    ├─ 头顺序 (4,1,5,3,0,2,6) → 收缩压3位 / 舒张压2位 / 脉搏2位
    └─ 合理性过滤：收缩压 60~260、舒张压 30~160、脉搏 30~220、且收缩压 > 舒张压
 → 81 组测试时增强（3 尺度 × 3 宽比例 × 3 横向平移 × 3 纵向平移）
 → 加权投票：得分 = 该读数置信度之和 + 0.5 × 票数
 → 胜出读数 + 一组可信度信号

5.4.2 为什么需要 81 组增强

该数字模型对取景边距极度敏感：在人工标注框上准确率 94.7%，换成检测框就掉到 63%。多尺度试探 + 按"模型自己更自信"加权投票，能在不重训模型的前提下把损失捞回来——离线 60 张真实照片三项全对 74.1%。

5.4.3 可信度信号与"请核对"门禁

识别成功 ≠ 识别可信。血压计读错时给的是"看着很合理"的错值（真值 119/86/63 读成 121/82/60），用户看不出来就存了——比识别失败更危险。因此识别后还要判断可信度：

信号含义
agree81 次尝试里有多大比例读出了同一个结果（最强信号）
detConf液晶屏定位框置信度
variants / weightShare / margin候选读法种数、置信度占比、与第二名的差距
meanGeo7 个数字头最大概率的几何均值（实测无区分度，仅用于日志）

判据不是拍脑袋定的，而是用 60 张真实照片（文件名即真值）跑完整 81 组增强标定出来的：

判据抓到错值误标正确结果
agree < 0.30 或 detConf < 0.30（当前采用）14/15（93%）4/43（9.3%）
只看 agree < 0.3012/15（80%）3/43（7.0%）
只看 meanGeo（曾被误用）—100%（等于提示失效）
门禁是硬拦截：命中判据时表单顶部出现"识别结果请核对"（含人话原因，如"没能稳定地找到血压计屏幕（定位把握 13%）"）， 此时点保存会被拦下并提示"请先核对识别结果"；点"我已核对"后才能保存。用户自己改了数值也视为已核对，撤掉提示不反复打扰。
真机四象限验收：低置信度+错值 → 出提示 ✅；不确认点保存 → 记录数不变 ✅；确认后保存 → +1 ✅；高置信度 → 不打扰 ✅。

5.4.4 兜底链策略（诚实的取舍）

新链路失败时会依次回退到：通用七段识别器 → 欧姆龙专用检测 → 通用数字区域检测 → ML Kit 通用 OCR。

兜底链的实测结论：它们没有可信度信号，而且会给出"看着合理"的错值——真机实测真值 117/80/57 被读成 116/66 且当时没有任何提示，用户直接就存了； 那一次总耗时 77 秒（新链路正常时约 12 秒）。 现已强制规定：兜底链的结果一律标记 fromFallback，必须人工核对。 是否彻底砍掉兜底链，等分阶段耗时日志积累数据后再定。

5.4.5 识别准确率实测

场景结果
合成七段图基准（192 张）新链路 100%（干净 48/48、退化 144/144）；旧链路 0%
