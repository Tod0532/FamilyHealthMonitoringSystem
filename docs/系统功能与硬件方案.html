图 3　血压链路：不改装血压计，只借手机相机

3.1 硬件拓扑（含接口与电压）

图 5　硬件拓扑：一颗芯片同时承担 BLE 主机与 WiFi 上报，省掉两颗转换芯片

3.2 器件选型理由

部件规格为什么选它 / 注意点
主控模组ESP32-S3-WROOM-1（双核 LX7 @240MHz，BLE 5 + WiFi 2.4G，8MB Flash）一颗芯片同时做 BLE 主机与 WiFi，不用"蓝牙转串口 + 串口转 WiFi"两颗；实测固件只占 RAM 15.8%、Flash 32.5%，N8 版本足够、不需要 PSRAM
USB-UART 桥CP2102N（板载）给 PC 提供烧写与串口日志；需装 Silicon Labs 驱动（本项目已装 v10.1.8.2466）
心率源手环 / 心率胸带，须对外暴露标准 0x180D走标准协议就不用破解私有格式；胸带更适合长期测试（戴上就持续广播、摘下即停，能如实反映"数据停了"）
供电5V USB 或板级 DC（视 PCBA 而定）BLE+WiFi 共存时电流尖峰高，建议独立 5V/2A
血压采集任意七段显示的电子血压计 + 手机零改造接入；但 OCR 对机型字体敏感，换机型必须重新验证

3.5 硬件侧风险与对策

风险现象对策
企业级 WiFi 连不上家网是 WPA2-Enterprise(802.1X)，固件只实现 PSK用一个自开 WPA2-PSK + NAT 的小路由器，板子/手机/电脑都挂它；顺带绕过企业网的客户端隔离
BLE 与 WiFi 抢 2.4G距离远时上报间歇丢失网关靠近手环；选带 IPEX 外置天线口的板；天线别贴金属
供电跌落随机重启、连上就掉，串口日志却正常独立 5V/2A + USB 电流表看瞬时压降
BLE 单连接板子连上手环后手机连不上协议特性非故障：调试看板子串口或 BLE 嗅探器
一网关一源多人家庭需多块板固件扩展多连接即可（已配置 MAX_CONNECTIONS=2）

4.4 设备鉴权五步

步骤发起方接口关键约束
① 生成绑定码AppPOST /api/device/bind-code6 位数字，10 分钟有效、只能用一次，绑定时指定归属成员
② 换令牌板子POST /api/device/bind提交 bindCode + deviceSn + 固件版本 → 返回 deviceToken，只返回一次
③ 落盘板子—写入 NVS；服务端只存令牌的 SHA-256，不存明文
④ 日常上报板子POST /api/device/health-data请求头 X-Device-Token
⑤ 解绑AppDELETE /api/device/{id}令牌立即失效；板子下次上报收到 401 并清空本地令牌
这样固件里没有任何用户凭据，板子丢了拿不到账号；用户随时能一键解绑。

5.4 曲线与省电策略

滚动窗口

只保留最近 30 分钟、最多 200 点；同一时刻重复上报不重复描点（值变了则覆盖）

换设备清空

切换设备时清空曲线，否则会把两个成员的读数连成一条线

不做闪烁动画

刻意不做呼吸灯：一直闪会让人以为数据在实时跳动，而"是否真在刷新"正是本页最该说清的事

6.2 落库节流的关键参数

参数取值含义
HR_STORE_DELTA_BPM3心率变化达到 3bpm 就入库

6.3 预警冷却：为什么必须做，以及"回落又升高"怎么算

被吞掉 而这恰恰是最该提醒的情况。所以冷却键里带上"异常是否仍在持续"：上一条也异常才算延续，上一条正常就算新事件 该状态存内存（重启后为空 → 首个异常多记一条）：刻意选"宁可多记、不可漏报"的失败方向

7.1 完整流水线（含失败回退分支）

↓

↓

7.2 为什么要 81 组增强

该数字模型对取景边距极度敏感：在人工标注框上准确率 94.7%，换成检测框就掉到 63%。于是对同一个框做多尺度、多平移的试探，再按"模型自己更自信"加权投票。

图 19　81 组增强的构成与投票公式（Dart 与标定脚本必须保持一致）

7.3 识别准确率实测

图 20　三项全对率（收缩压/舒张压/脉搏同时正确）。注意：74.1% 是在这 60 张上拟合的成绩，换机型未验证

7.4 可信度阈值是怎么标定出来的

识别成功 ≠ 识别可信。血压计读错时给的是"看着很合理"的错值（真值 119/86/63 读成 121/82/60），用户看不出来就存了。所以要用"81 组尝试的一致性"来判断这次读数可不可信。

图 21　阈值权衡：取 0.30 时抓到 14/15（93%）个错值，只误标 4/43（9.3%）的正确结果
判据抓到错值误标正确说明
agree < 0.30 或 detConf < 0.3014/15（93%）4/43（9.3%）当前采用
只看 agree < 0.3012/15（80%）3/43（7.0%）少抓 2 个"高一致度但框不准"
用 meanGeo（曾被误用）—100%实测对 0.212–0.232 / 错 0.180–0.230，几乎完全重叠 → 任何阈值都会把全部结果标成"请核对"，提示等于失效
标定的价值就在于这条否定结论：最初凭直觉把"数字模型置信度"写进判据，是错的。用 60 张真实照片跑完整 81 组增强后才看出来它没有区分度。

11风险矩阵与后续计划

图 28　风险矩阵：右上角两项（固件未上板、OCR 泛化）是当前最该先解决的

11.1 已知限制（如实记录）

#限制影响
1固件从未在真板上运行过（只编译过）上板后可能暴露 BLE 时序、供电、射频共存等运行时问题
2OCR 两个模型就是在这 60 张照片上训练/验证的74.1% 是"拟合成绩"，换机型/换字体可能明显下降
3兜底识别链低效（一次 77 秒）且无质量信号已强制"兜底结果必须核对"，但体验仍差
4家里是 WPA2-Enterprise，固件只支持 PSK联网上报暂时做不到，需自开 PSK 网络
5阿里云后端是旧版本，没有设备接入接口只能连本地后端；走公网需先做生产部署
6注册验证码未做任何校验任意 6 位可注册任意手机号，上线前必须决策
7生产凭据（DB 口令 / JWT 密钥 / 签名口令）需更换并外置见 docs/上线前安全整改.md
8预警只写库，不主动推送用户不打开 App 就不知道异常
9一个网关只连一个心率源多人家庭需多板，或先把固件改成多连接

11.2 后续计划（按优先级）

  1. 上真板验证：烧写 → 串口验 BLE → 解决联网 → 端到端跑通"手环→板子→服务器→App"。
  2. 固件多连接：一块网关同时连 2 个手环（MAX_CONNECTIONS=2 已配置，需改代码）。
  3. OCR 泛化验证：另买一台不同品牌血压计，量化"换机型掉多少"。
  4. OCR 提速 / 砍兜底链：等分阶段计时日志积累数据后决定。
  5. 预警推送到手机：先做轮询到新预警发本地通知，后续再考虑服务端长连接。
  6. 数据留存策略：确定 5 秒级原始数据保留多久、是否降采样；用 EXPLAIN 取证决定索引。
  7. 上线前安全整改：验证码、生产凭据轮换、Android 签名口令外置。
