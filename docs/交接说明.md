## 二、心率实时监控（本轮三件事都已做完）


烧写方案见 `docs/ESP32烧写与联调方案.md`。

### ② App：心率实时监控页 ✅

- 新增页：`flutter-app/lib/app/modules/profile/heart_rate_monitor_page.dart`
- 路由 `/profile/heart-rate`；入口两处：**我的 → 设备 → 心率实时监控**、
  设备管理页的「查看心率实时监控」按钮
- 轮询 `GET /api/device/latest`，间隔 **3 秒**；`dispose()` 停表，另外还监听
  `didChangeAppLifecycleState` —— 本页是 push 出来的路由，退到后台**不会**触发
  dispose，只靠 dispose 会息屏后继续每 3 秒请求（费电）
- 显示：大号心率、`更新于 x 秒前`、连接状态（已连接 / 数据已停止 / 设备离线）、
  fl_chart 滚动曲线（最近 30 分钟，最多 200 点）
- 后端 `stale`（>20 秒无新值）时**不把旧值当实时值**，只显示 `--` 并提示
- 单请求超时 2 秒（必须 < 轮询间隔，否则请求会叠在一起排队）

### ③ 服务端：落库节流 ✅（外加一个必须补的实时值缓存）

`DeviceServiceImpl.report()`：变化 ≥3bpm **或** 距上次入库 >60 秒才写 `health_data`，
其余只刷新内存实时值。

> **关键点：只做节流会把实时监控页弄坏。**
> `/api/device/latest` 原本查库里"最新一条"，节流后库里最多滞后 60 秒 →
> 页面会一直显示旧值。所以同时加了 `REALTIME`
> （`Map<设备id, 不可变快照>`，`ConcurrentHashMap`）：**每次上报都刷新**，
> `listLatest` 优先取缓存、缓存为空才回退查库。实时值因此不受节流影响（仍是秒级），
> 而历史趋势只落"有意义的点"。

其它细节：

- 节流**只针对 `heart_rate`**；其它数据类型量小，照旧全量入库
- 进程重启后缓存为空，此时以库里最新一条作节流基准，避免重启后再连写一串
- `elapsed < 0`（设备时钟比服务端快、measureTime 落在将来）按"间隔到了"处理，
  否则时间差永远为负、永远不入库，等于静默掐死这条链路
- 解绑时清掉该设备的实时值，避免解绑后还显示旧读数
- 单测 `src/test/java/com/health/service/impl/DeviceReportThrottleTest.java`（5 用例全过）。
  坑：`AlertEvaluator` 是**字段级 `@Autowired`**，`@InjectMocks` 不会注入它（实测 NPE），
  测试里要 `ReflectionTestUtils.setField` 显式补
- 端到端冒烟 `src/test/smoke-realtime.ps1`（4 项判定全过）：读数一直在变、
  `ageSeconds ≤4`、**8 次上报只落库 2 行**、停报 25 秒后 `stale=true`

## 三、本项目踩过的坑（务必先读，能省几小时）

### OCR 相关

1. **仓库里早有训好的可用模型**，不要再手搓识别算法 ✗。
   手搓的七段流水线（`tool/segment_fit.dart`）试了四种做法全部 0~2%，已作废。
   正确链路见 `lib/core/ocr/services/lcd_onnx_pipeline.dart`。
2. **多输出 TFLite 调用**必须三条同时满足：`runForMultipleInputs` +
   `Map<int,Object>` 传参 + 每个输出形状 **`[1,10]`**（带 batch 维）。
   这是 `bpressure_multihead.tflite` 的 7 个输出头。
   **App 里原有的 `BpTfliteDetector` 也犯了这个错，从未成功调用过** ✗。
3. **模型资产要在 pubspec 里注册**，否则不打进 APK
   （`lcd_detector.onnx` 那行曾被注释掉，真机表现为"模型未就绪"）。
4. **Flutter 版 onnxruntime 算子不全**（缺 YOLOv8 检测头的 Reshape），
   已改用 onnx2tf 转出的 TFLite；转换前后输出逐位一致。
5. **数字模型对取景边距很敏感**：训练取景 94.7%、检测框仅 63%，
   必须做多尺度 TTA 投票才能到 71.7%。

### 后端相关

6. **两层鉴权都要放行**：Spring Security 与自定义 `RoleInterceptor` 都拦 `/api/**`，
   设备端接口（`/api/device/bind|health-data|heartbeat`）只改一层仍会 403。
7. **写 `health_data` 必须带 `family_id`**，否则记录入库但 App 列表看不到
   （列表按 family_id 过滤）。
8. **`AlertEvaluator` 原本不存在** ✗ —— 规则只存不评估，`alert_record` 永远为空。
   已补（`service/impl/AlertEvaluator.java`），设备上报处已接入。
9. **查"最新一条"要加 id 兜底排序**：只按 `measure_time` 排序时，
   同一秒多条记录会取回旧值（实测先报 75 再报 128 却返回 75）。
13. **`/api/health-data` 的 `data` 是数组，不是分页对象** ——
   写成 `$resp.data.records` 会**静默**得到空数组（不报错），
   冒烟脚本因此报过"落库 0 行"的假失败。分页对象那套只在别处出现。
14. **只做落库节流会把实时监控页弄坏**：`/api/device/latest` 原本查库里
   "最新一条"，节流后库里最多滞后 60 秒，页面就一直显示旧值。
   必须同时维护内存实时值（见「二·③」），节流只作用于历史入库。
15. **`@InjectMocks` 不注入字段级 `@Autowired`**：`DeviceServiceImpl.alertEvaluator`
   是字段注入（不在构造器里），单测里必须 `ReflectionTestUtils.setField` 显式补，
   否则 NPE。

### 真机调试相关

10. **adb 连不上先看授权**：`adb kill-server && adb start-server` 会触发手机上的授权弹窗；
    手机不在前台时 `uiautomator dump` 可能是过期缓存。
11. **`pm clear` 后会重置权限**，相册权限弹窗会挡住 OCR 流程；
    用 `adb shell pm grant <包名> android.permission.READ_MEDIA_IMAGES` 直接授权更可靠。
12. **看不了图**（当前模型不接受图像输入）—— 验证 UI 改动时用
    **截图像素分析**或 uiautomator 文本做交叉验证；嵌套 Text 可能不被 uiautomator 暴露。

### 冒烟脚本相关（PS 5.1 的坑）

13. **含中文的 `.ps1` 必须存成 UTF-8 带 BOM**，否则 PS 5.1 按 GBK 读会解析失败；
    `[System.IO.File]::*` 要用绝对路径。
    **注意：编辑工具会把 BOM 去掉**，改完 `smoke-*.ps1` 要重新用
    `[System.Management.Automation.Language.Parser]::ParseFile` 校验一次再跑。
14. **PS 5.1 里别用 `Invoke-RestMethod` 轮询**：实测会**卡死** ——
    进程停在 13 个线程全 `Wait`、没有任何 socket 的挂起态，脚本跑到一半不动，
    且没有任何报错。冒烟脚本一律改用系统自带的 **`curl.exe`**
    （封装见 `src/test/smoke-http.ps1`）。
15. **PS 5.1 向原生命令传参会吞掉 JSON 里的双引号**，后端会报"请求体格式错误"；
    必须把请求体写成临时文件，用 `--data-binary @file` 传。

### P0-2 真机验收：✅ 11 项全过，并修掉一个**只有真机才暴露的崩溃**

**发现的 bug**：`heart_rate_monitor_page.dart` 的 `_timer` 写成了 `late final`，
但退到后台再回前台时会**第二次赋值** → 运行时抛
`LateInitializationError: Field '_timer' has already been initialized.`。
`flutter analyze`（0 error）与 APK 编译**都不报**。
更阴的是：赋值右半段 `Timer.periodic(...)` 已先执行完，异常一抛这个新 Timer
就再没引用 —— 漏出一个**永远不会被 cancel 的 3 秒定时器**，此后一直请求到 App 退出，
恰好是这段代码注释里想避免的"一晚上把电耗光"。

### P0-1 预警去重：✅ 完成

**问题量化（实测，非估算）**：spike 场景上报 **14 次 → 新增 14 条**预警，1:1；
记录时间戳正好相差 5 秒。按 5 秒上报推算 **约 1.7 万条/天/成员**，预警功能等于失效。

**做法**：命中后先判断"是不是同一次异常事件的延续" —— 延续且距上次记录
< 冷却窗口（danger 3 分钟 / 其余 30 分钟）则**不新建**，只把那条 `update_time` 前移；
**回落正常后再超标算新事件**（否则"降下来又升上去"会被吞掉，而这最该提醒）。
"是否仍在持续"存在内存（`AlertEvaluator.LAST_VIOLATED`）：重启后为空 → 首个异常
多记一条。这是刻意选的失败方向 —— 宁可多记一条，不可静默漏报。

**验证**：新增单测 `AlertDedupTest` **7/7 通过**；把去重逻辑临时关掉做变异测试 →
3 个用例失败（证明单测不是空转）；冒烟新增第 8 步 → 7 次超标上报只新增 1 条 ✅。
索引 `(user_id, rule_id, create_time)` 进了 `db/schema.sql` 与 `schema-h2.sql`，
线上增量脚本 `db/migration-alert-dedup.sql`（幂等；**索引先上，代码后上**）。

19. **`edit` 工具会剥掉 UTF-8 BOM** —— 改完任何含中文的 `.ps1`，

## 九、P1-1 低置信度识别提示（已完成）

### 要解决的问题
识别**成功**≠识别**可信**。血压计读错时给的是"看着很合理"的错值
（实测真值 119/86/63 读成 121/82/60），用户看不出来就存了 —— 比识别失败更危险。

### 阈值是标定出来的
`flutter-app/tool/confidence_calibration.py`：60 张真实照片跑完整 81 组 TTA，
量各信号在"三项全对 / 有错"两组上的分布。**结论里最值钱的一条是否定结论**：
数字模型置信度 `meanGeo` **没有区分度**（对 0.212~0.232、错 0.180~0.230，
几乎完全重叠），任何 ≥0.25 的阈值都会把 100% 的结果标成"请核对"。
最初凭直觉把它写进判据是错的 —— 这就是必须标定的理由。

最终判据：**`agree < 0.30 或 detConf < 0.30`** →
抓到 **14/15（93%）** 个错值，误标 **4/43（9.3%）** 个正确结果。
`meanGeo` 只留在 `debugLabel` 里供排查。

### 交互上的两个取舍
1. **只用"低置信度才提示"**，不是每次拍照都要求确认 ——
   否则用户每天多点几下，几天后就条件反射地直接点确认，提示等于失效。
2. **提示必须是硬拦截**：不点「我已核对」就保存，会被拦下并提示
   「请先核对识别结果」。只提示不拦，错值照样进档案。
   用户自己改了数值即视为已核对（撤掉提示），不反复打扰。

### 真机验收（SM02G4061983569，四象限都覆盖）
| 场景 | 结果 |
|---|---|
| 低置信度 + 识别错（98-68-80 真值 98/68/80 → 识别 140/85/71） | ✅ 出现「识别结果请核对」+「没能稳定地找到血压计屏幕（定位把握 13%）」 |
| 不点「我已核对」直接保存 | ✅ 记录数不变（5），提示「请先核对识别结果」 |
| 点「我已核对」后保存 | ✅ 记录数 5→6，值为 140/85 |
| 高置信度结果 | ✅ 不打扰（无提示条） |

### 缺口一已补（兜底链强制核对），缺口二仍在
1. ~~**提示只覆盖新链路**~~ **已修**：新链路失败会回退到通用七段/欧姆龙/通用数字检测，
   这些兜底链没有可信度信号，原来 `needsReview=false` 于是**不提示** ——
   真机实测把真值 117/80/57 读成 116/66 且直接放行。现在兜底结果一律带
   `fromFallback`，`needsReview` 恒为 true，提示文案是
   「这次用的是备用识别方式，可信度无法评估，识别结果请核对」。
   （真机复验待做：手机锁屏需要 PIN）
2. **"自信地读错"抓不到**：错读里一致度高达 0.99 的那些（如真值 117-80-57
   读成 104/73/75），任何置信度信号都无法区分，只能靠用户对着屏幕核对 ——
   提示文案就是为此写的。
3. 兜底链"低收益高耗时"（离线 60 张真实照片上旧链路三项全对率约 0%，
   真机一次 77 秒）。要不要直接砍掉，等这轮加的分阶段计时日志出数据再定。

### 本轮新增的坑（接第 20 条）
21. **不要用 Python `multiprocessing` / `ProcessPoolExecutor`**：本机实测子进程
    会被杀，父进程报 `BrokenProcessPool: A process in the process pool was
    terminated abruptly`（Windows 上多进程靠命名管道传数据，这个环境不允许）。
    正确做法：`--shard i/n` 开多个独立进程（由 shell 启动，各写各的 JSONL），
    `--resume` 补没跑完的，`--analyze` 合并分析。
    **另外**：启动分片的那个 shell 一旦被超时杀掉，分片会跟着一起死
    （Windows 作业对象），所以分片任务要放到后台跑、别挂在会超时的前台命令里。
22. **Python 侧单次数字模型推理约 1.2 秒**（1 线程），一张照片 81 组 TTA ≈ 100 秒，
    60 张单进程要 100 分钟。标定脚本因此必须多进程分片。
    顺便说明：App 端快得多（有 XNNPACK/多线程），但真机上"新链路失败 → 回退旧链路"
    那一次实测花了 **77 秒**，这是要单独优化的体验问题（见"下一步"）。
23. **真机喂图给 App 的流程**（验收 OCR 时用）：
    ① `adb push` 照片到 `/sdcard/Pictures/RHI/`
    ② `am broadcast -a android.intent.action.MEDIA_SCANNER_SCAN_FILE -d file://...`
       （不做这一步相册看不到）
    ③ 把文件 mtime 设成当前时间，它会排到相册第一格，位置固定为 (199,1230)
    ④ 系统相册是**多选**：点第一格 → 再点右下角「完成」(1008,2447)
    ⑤ 随后 App 里还有个「识别成功，是否自动填充？」弹窗，点「确认填充」(840,1678)
    —— **用识别出的数值反查是否选对了照片**，别只看"有结果"就当选对了。
24. **`write` 工具写的 `.ps1` 没有 BOM**，里面如果有中文，PS 5.1 按 GBK 读会报
    一堆"缺少括号/字符串未终止"的解析错误（第 13 条的再次踩坑）。
    给 Windows 写的一次性小脚本**宁可全用 ASCII**，比事后补 BOM 省事。

## 十一、OCR 精度：实验台、实测结论与真正的提升路径

### 11.1 先说结论
**不重训模型的前提下，识别准确率的天花板大约是 74%**（三项全对，60 张真实照片）。
本轮能做的、也确实做了的是：**把"认不准"的结果拦下来**，
让"填进表单的血压值"准确率从 **74.1% 提升到 93.2%**（代价：约 24% 的照片需要重拍/手输）。

### 11.2 实验台：lutter-app/tool/ocr_lab.py
改 OCR 参数最大的风险是"改了个数、以为变好了"。而跑一次完整 81 组增强要 ~100 秒/张，
60 张就是 100 分钟，没法迭代。所以先做实验台：

  一次性把每张照片在 **201 个候选取景框**（200 个网格 + 1 个标注框）下的
  **7 头 logits** 全部缓存 → 之后任何策略都只读缓存、**瞬间**出准确率。

`ash
# 预计算（24 个单线程分片，约 10 分钟；8 进程×4 线程实测反而更慢）
powershell -File $env:TEMP\run_ocr_lab2.ps1        # 或手工：
#   for i in 0..23: python tool/ocr_lab.py --prep --resume --shard /24
python tool/ocr_lab.py --report      # 取景/投票/选择/弃权 三张对比表
python tool/ocr_lab.py --tiers       # 按 agree 分档的准确率（定阈值用）
python tool/ocr_lab.py --grids       # 网格规模 vs 准确率（定耗时用）
python tool/ocr_lab.py --signals     # 各信号在对/错两组的分布
`
辅助脚本：ox_quality.py（取景 IoU）、ox_ratio.py（标注框/检测框比例）、
equality_check.py（重编码是否影响检测）。

### 11.3 实测结论（60 张真实照片，全部可复现）

| 策略 | 候选数 | 三项全对 | 备注 |
|---|---|---|---|
| 取景上界（只用标注框） | 1 | **92.7%**（51/55） | 取景完美时的天花板 |
| 现状 81 组投票 | 81 | **74.1%** | App 当前实现 |
| 3 尺度 × 5×5 平移 | 75 | 74.1% | 候选更少，成绩持平 |
| 5 尺度 × 3×3 | 45 | 72.4% | |
| 5 尺度 × 5×5 | 125 | 72.4% | 候选再多也不涨 |
| 8 尺度 × 5×5 | 200 | 72.4% | |
| 只 8 尺度、不平移 | 8 | 69.0% | 平移比尺度重要 |
| 取单个最自信候选 | 200 | 74.1% | 不优于投票 |
| 投票系数 coef=0/1/2、均值权重、生理先验 | — | 72.4% | 全都没差别 |
| **投票 + agree<0.30 弃权** | 75 | **填出值准确率 93.2%**（覆盖 76%） | 本轮采用的策略 |

### 11.4 三个否定结论（别再重复试）
1. **取景不是系统性偏移，不能靠固定校正修掉。**
   标注框与检测框的 IoU 中位 0.851、只有 23% ≥0.90；但标注框只比检测框小 1.5~3%
   （中位面积比 0.971）。逐轴仿射校正（calibrate_boxes.py）在 60 张上变好 31 / 变差 28 → 无效。
   ⇒ 取景误差是**每张照片各不相同的随机偏差**，所以"多尺度投票"的思路是对的。
2. **网格加密没有收益。** 27→75→125→200 个候选分别是 70.7% / 74.1% / 72.4% / 72.4%，
   而推理量正比于候选数 ⇒ 不要为了精度加大网格（只会更慢）。
3. **"取最自信候选"不优于投票。** 初测它显示 81~82.8%，查出来是方法学漏洞：
   候选池里混进了**标注框**（训练取景），模型当然在它上面最自信 —— 那是推理时拿不到的信息。
   剔除后立刻回到 74.1%。**以后做这类实验，先检查候选池有没有作弊。**

### 11.5 已落地的改动
1. **三档策略**（lib/core/ocr/models/ocr_quality.dart）：
   - gree ≥ 0.40 且屏幕框置信度正常 → 直接填值，不打扰
   -  .30 ≤ agree < 0.40 或 detConf < 0.30 → 填值 + 要求"我已核对"
   - gree < 0.30 → **拒绝填值**：清空输入框 + 提示重拍/手动输入
2. **新链路改用原图**（seven_segment_ocr_service.dart）：
   原来会先被旧的 BloodPressureScreenDetector 裁一刀再交给新链路；
   新链路自带定位 + 81 组多尺度试探，不需要预裁剪，而旧检测器不可靠
   （真机观察到同一张照片检测置信度从离线 0.95 掉到 0.13，最可能就是这个原因）。
   旧链路的几段仍用裁过的图。
3. 排除一个怀疑：App 的 imageQuality=85 重编码**不影响**检测
   （equality_check.py：框 IoU 中位 0.996、置信度差 ≤0.012）。

### 11.6 真要继续提准确率，该做什么（按性价比）
1. **重训数字模型，用"检测框式取景"做增强**（最大杠杆）。
   现在模型只见过标注框取景（94.7%），换成检测框就掉到 63%；
   如果把训练裁剪做成"标注框 + 随机缩放/平移"（模拟检测框误差），
   模型就不再依赖某种特定取景 —— 这是把 74% 往 90% 推的唯一靠谱路径。
   前提：需要训练代码与算力（仓库里目前只有推理和评估脚本）。
2. **加标注数据。** 现在只有 60 张照片 / 63 个屏幕框，太少；同机型多拍几十张、多机型各拍一批。
3. **换更好的检测器**（或在检测框内再加一级"数字区域"定位），把"取景上界"从 92.7% 往上推。
4. **真机上重新标阈值**。离线 agree 与真机 agree 的分布可能不同
   （同一张照片离线 0.13 / 真机 0.42），阈值应在**真机采集的数据**上复核一遍。
5. 兜底链已经证明是低收益高耗时（一次 77 秒），建议直接砍掉，失败就报"请重拍"。
