1.2 需求的本质归纳

散落的诉求其实收敛为三件事：

  1. 数据来源自动化（R1 拍照、R2 手环）—— 减少手工录入，这是产品的核心价值
  2. 数据可信与安全（R6、R8）—— 上线前提
  3. 可交付与可维护（R7）—— 让后续接手的人能改、能验

二、方案设计

2.1 R2：设备接入体系（本次重点）

问题：现有固件用"账号+口令登录"向后端写数据。板子一旦被拆开，账号口令就泄露， 且令牌权限过大（能改资料、能看全家数据）。不适合量产。

方案：一次性绑定码 → 设备令牌（最小权限）

接口设计

接口鉴权说明
POST /api/device/bind绑定码入参 bindCode、deviceSn、deviceName；返回 deviceToken、memberId
POST /api/device/health-data设备令牌入参 dataType、value1、value2、measureTime；只能写，不能读
POST /api/device/heartbeat设备令牌上报在线状态、信号强度、电池（用于 App 显示设备是否在线）
GET/DELETE /api/device用户 JWTApp 查已绑定设备 / 解绑（解绑即令牌失效）
POST /api/device/bind-code用户 JWTApp 生成绑定码（绑定到指定成员）

数据模型

device
  id, user_id, member_id, device_sn(唯一), device_name, device_type
  token_hash          -- 只存哈希，防拖库
  bind_code, bind_code_expire
  last_seen, status, firmware_version, created_at

health_data 已有 data_source 字段：设备写入时置 device，并可选加 device_id。

App 侧

  • 我的 →「设备管理」：生成绑定码（大字 + 二维码）、已绑定设备列表（在线状态 / 最近上报时间 / 解绑）
  • 健康数据列表：设备来源的记录加"设备"标签，与手工录入区分

固件侧（v2）

  • 首次上电：BLE 配网（或过渡期保留硬编码 WiFi）+ 输入绑定码 → 换令牌 → 存 NVS
  • 上报改用 X-Device-Token，不再使用账号口令
  • 断网缓存持久化到 NVS（现在只在内存，断电即丢）

三、分阶段计划

P0 · 打通"手环 → 服务器 → App"（预计 1.5 天）

任务产出验收标准

P0 完成即达成：心率数据从手环到 App 全自动，不依赖手机常开、不把账号口令放进硬件。

P1 · OCR 收尾（预计 1 天）

  1. 真机验证（前置条件：手机上点"允许 USB 调试"）
  2. 用 60 张做真实退化增强 → 微调多头模型 → 在 15 张 holdout 上评估
  3. 把基准脚本（eval_lcd_detector.py / eval_multihead.py / e2e_pipeline.py）写成一条命令的回归

验收：holdout 上三项全对 ≥85%；回归脚本可一键复现。

P2 · 上线前安全（预计 1 天，含你的决策）

验证码方案（接短信 / 明确免验证）→ 凭据清理 → 排序规则统一 → 重新部署并冒烟。

P3 · 资产与文档（预计 0.5 天）

真实照片入库（LFS 或压缩）→ 使用说明补"硬件接入"章节（含配网/绑定/排查流程图）→ 更新 README。

P4 · 完整性与体验（可选，按需排）

  • 预警真实推送（当前只有 App 内列表）：接入极光/个推，或服务端 + 手机通知
  • 未验证功能补齐：扫码加入家庭、测量提醒触发
  • 设备侧扩展：从手环健康服务里再订阅血氧/步数

四、风险与依赖

风险影响应对
手环只允许一个主机连接板子连着时 App 连不上手环采集固定交给板子，App 只读服务器数据（当前方案已规避）
ESP32 仅支持 2.4GHz WiFi家里若只有 5GHz 连不上固件说明已标注；必要时加 BLE 配网提示
设备令牌泄露他人可伪造健康数据令牌只存哈希、仅允许写、App 可随时解绑
模型过拟合这 60 张换机型准确率骤降引入不同机型的少量新照片做验证；增强训练
手机 USB 授权OCR 真机验证与部分联调阻塞一次性人工确认
数据只在本机换设备即丢失 60 张原始数据P3 入库（建议 LFS）
